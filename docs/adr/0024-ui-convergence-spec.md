# ADR-0024: UI convergence spec — visual identity, typography, motion, and control reuse

The 2026-10-27 UI refactor landed fifteen code changes (C1–C15) that each fixed a concrete
defect, but the repo had no document saying _why_ any of them were the right shape. Without one,
every future PR re-litigates the same questions: may an activity-bar icon be a plain button?
Where does a new input come from? Is 10px text acceptable? This ADR is the normative
restatement of those fifteen changes plus the four spec gaps the design review found missing
(C16 visual identity, C17 typography, C18 motion, C19 control reuse), so the rules survive
independently of the branch that introduced them.

- **Status:** Accepted
- **Decided:** 2026-10-29
- **Supersedes:** nothing. ADR-0013 §13 (shared search UI) and ADR-0023 (search surfaces) remain
  authoritative for search behaviour; this ADR owns the _chrome_ those surfaces sit in.
- **Amends:** ADR-0013 decision #9 is further narrowed — the sidebar query field is no longer a
  hand-written `<input>`, it is the shared `SearchInput` (§4).
- **Reverses (2026-10-30):** the design doc §4 R3 rule "预览不提供常驻顶部工具条", and that doc's
  single-shared-top-band layout model. Both are replaced by §10 (each pane owns its own toolbar).

## 1. Visual identity

### 1.1 Palette: the cool-blue system (decided 2026-10-30)

The old accent `--color-accent: #5e6ad2` (Radix `indigo-9`) read as a generic admin-dashboard
default and belonged to **no system** — neutral-grey chrome with a foreign indigo pinned onto it.
The review diagrams (`docs.local/…/images/*.svg`) use one coherent **cool-blue** system instead,
and that coherence — not any single colour — is why they read better than the app did. **The
diagrams' palette is adopted as the product palette**, subject to one accessibility correction.

Measured from the SVG fills, the diagrams use: accent `#2563eb` (blue-600), blue-tinted page
backgrounds `#f4f7fb`–`#f8fafd`, slate text steps `#1f2937` / `#637083` / `#68778d` / `#8893a2` /
`#94a3b8`, accent tint `#eaf2ff`, and semantics `#16845b` / `#c63d45` / `#b66a00`.

**The accessibility correction (mandatory).** The diagrams' two lightest slate steps are **not
shippable**: `#94a3b8` on `#f5f7fb` is **2.39:1** and `#8893a2` also fails the 4.5:1 floor of
§7.1. Copying them verbatim would re-introduce the exact violation §7.1 exists to prevent. Dark
keeps two steps (`#a0adbd` = **8.12:1**, `#8893a2` = **5.94:1**, both on `#0f1419`) because its
background is dark and there is headroom.

**Amended 2026-10-31 — the light muted step is `#536176`, not `#637083`.** The muted step must
clear 4.5:1 against **every** surface in §1.2, not just `bg`: `#637083` measures 4.69:1 on
`#f5f7fb` but **4.47:1 on `#edf2f9`** and **4.46:1 on `#eaf2ff`** — it fails on the hover fill and
on the selected-state fill, both of which carry muted text in normal use. The diagrams' own
dominant muted slate is `#536176` (83 occurrences, versus 24 for `#637083`); it measures
**5.86 / 6.29 / 5.59 / 5.58** on `bg` / `surface` / `surface-overlay` / `accent-muted`. Faithfulness
to the artwork and the contrast floor therefore point at the same value.

**Forbidden:** adding a muted grey lighter than the compliant floor to the light theme "because the
diagram has one". The floor is `L ≤ 0.1575` (the lightest compliant value is ≈ `#616d7f`); diagram
greys `#68778d` (4.25:1), `#94a3b8` (2.39:1) and `#a2acbb` (2.14:1) are all below it. Note that
`#616d7f` is only **1.20:1** against `#536176` — imperceptible — which is why §11 item 3 keeps the
light theme collapsed to **one** muted step.

**Amended 2026-10-31 — semantic colours are indicators, not text, with one registered exception.**
`--color-danger`, `--color-success` and `--color-warning` are measured for the **indicator** role:
a **3:1** floor against every surface in §1.2 (WCAG 1.4.11). All six values clear it in both
themes — light minimum **3.69**, dark minimum **3.95** — so **no colour changes are needed.**
Status is then expressed by an adjacent glyph (`●` `✓` `⚠`) in the semantic colour plus neutral
text, never by colouring the text itself.

Serving as _text_ is arithmetically incompatible with the indicator role: on the dark theme a text
role needs `L ≥ 0.2555` while an indicator/fill role needs `L ≤ 0.1833` — mutually exclusive, so
one token cannot do both.

**The one exception: `--color-danger-text` (light `#b03039`, dark `#f87171`).** It must clear 4.5:1
on **every background a destructive menu item can occupy — including the hover/focus fill**, not
just the menu surface. Two pitfalls were hit while setting this value, both worth recording:

1. **Measure against the surfaces that ship _today_, not only the ones a pending palette migration
   will introduce.** C21 (the cold-blue swap) is not applied yet, so the live backgrounds are the
   old ones; a token landing now has to clear both sets.
2. **The hover fill is a background too.** `--color-danger-tint` is `color-mix(in srgb, var(--color-danger) 12%, transparent)`,
   and compositing it over the menu surface produces a _lighter_ background than the surface itself.

Measured (light, on today's surfaces): `#b03039` = **6.31** on `surface`, **5.89** on `bg`, **5.54**
on `surface-overlay`, **5.56** on `accent-muted`, **5.40** on the hover fill, **4.79** on the
hover-fill-over-`surface-overlay` composite. The last one is unreachable in practice (menu content
is `bg-[var(--color-surface)]`), but the value was chosen to clear it anyway so no caveat is needed
if a menu is ever re-hosted. Rejected candidates: `--color-danger` itself (`#c63d45` → 4.44 on
`surface-overlay`, 4.33 on the hover fill) and `#b8353d` (**4.41** on the hover-fill-over-overlay
composite). Dark `#f87171` clears everything at **5.08–6.83**.

`--color-danger-tint` is a **derived alias**, not a sixteenth palette value: it introduces no new
hex, only the 12% composite of `--color-danger`. The normative palette above therefore stays at
**15 values**.

**Disabled menu items are exempt from 1.4.3** ("inactive user interface components"). For the
record they measure 1.92:1 (light) / 2.04:1 (dark) at the `opacity-40` used by
`data-[disabled]:opacity-40` — compliant by exemption, not by contrast.

> **Finding (resolved 2026-10-31) — menu keyboard focus was only a ~1.1:1 background tint.**
> Both menu primitives use `outline-none` and convey keyboard focus solely by swapping the item
> background (`--color-surface-overlay`, or `--color-danger-tint` for destructive items). Measured
> against the menu surface those fill differences are **1.14 / 1.17:1 (light)** and
> **1.09 / 1.13:1 (dark)**.
>
> **Which SC applies — corrected after re-checking the sources.** The AA basis is
> **1.4.11 Non-text Contrast**: W3C's own technique C40 is registered as _sufficient for
> "identifying a user interface component's focus state"_ under 1.4.11, so a focus indicator that
> is the only cue must clear 3:1 against adjacent colours. **2.4.13 (Focus Appearance) also
> requires 3:1 plus a 2px perimeter, but it is Level AAA** — it must not be cited as the AA
> obligation. 2.4.7 (AA) only requires that an indicator _exists_. (An earlier draft of this
> document cited "1.4.11 / 2.4.13" as if both were AA; the 2.4.13 half was wrong and is
> withdrawn.)
>
> **Mainstream practice cuts the other way, and is not a defence.** shadcn/ui — whose `destructive`
> prop and class structure this repo's menu wrappers copy verbatim — Radix Themes and Linear all
> convey menu focus by background change alone. VS Code and macOS do too, but with a
> **contrast-tuned highlight token** rather than a faint surface step. "Everyone ships it this way"
> was already rejected as an argument in this document (§11, the destructive-menu item); the
> project's own bar is WCAG AA and its own C25 commitment is "focus indicator ≥3:1", so the
> ecosystem default does not settle it.
>
> **Resolution: adopted and implemented (2026-10-31).** The shared `.focus-ring` was added to all three
> menu-item components — `DropdownMenuItem`, `ContextMenuItem` and `ContextMenuCheckboxItem`. The
> objection that a ring makes menus heavier does not apply, because `.focus-ring` is gated on
> `:focus-visible` (`globals.css`): a pointer user who opens a menu and hovers keeps today's
> look exactly, while arrow-key navigation — the only case that needs the indicator — gets the
> 2px accent outline. It clears 3:1 in both themes, before and after C21 (accent `#5e6ad2` →
> **4.70** light / **3.70** dark; `#2563eb` → **5.17** / **3.28**). The background swap is **kept**:
> it is the hover/selection state, while the ring is the keyboard focus indicator.
> _Geometry to confirm visually:_ the ring's outer edge sits 4px outside the item box and the menu
> content is padded `p-1` (also 4px), so the ring lands exactly on the menu's own border — first and
> last items will sit flush against it. Recorded in PLAN C24 for the C13 visual pass.

Destructive menu items keep red text because the context-menu plan makes it a
requirement — 原则 4 "危险操作放最下方、用**警示色**、上方加分隔线，并二次确认", gate G5, and the
note that destructive items carry a _dual_ signal. Two facts make the red load-bearing rather than
decorative: (a) the promised `aria-*` half of that dual signal was never implemented, and WAI
defines **no** ARIA semantics for "dangerous" (there is no `aria-dangerous`), so the promise is
not satisfiable; (b) red destructive menu items are the mainstream pattern (macOS HIG, GitHub
Primer, Atlassian, Carbon). §1.2 forbids inventing new _greys for new surfaces_ — it does not
govern semantic text variants, so adding this token does not violate it.

**No alpha-discounted colour may carry state.** A state-bearing border or rule must meet 3:1 at
full opacity; `border-<color>/60` on a light background lands near 1.5:1 and fails. Only purely
decorative fills (a 10% hover tint) may be discounted.

**The `Button variant="destructive"` fill was removed** (2026-10-31). It was the only consumer of
`--color-danger` as a fill beneath white text (3.91:1 on the dark theme) and it had **zero
production call sites** — verified by deleting the union member and letting `tsc` enumerate every
consumer. Removing it deletes the fill/indicator conflict outright, which is why dark
`--color-danger` stays `#e5484d` rather than being darkened.

**Not adopted: the diagrams' purple `#7756d8` (34 occurrences).** In 图 02 it colours the _preview
pane bar_ and its icons while `#2563eb` colours the global bar — the diagrams use a two-accent
system. This spec keeps **one** accent. It is not rejected on accessibility grounds (it measures
4.77 / 5.11 / 4.55 / 4.54 on the four light surfaces, all compliant); it is rejected because
blue-plus-purple is the most common templated pairing in generated UI — the exact quality §1
exists to escape — and because the purple reads as a wireframe device for telling the reader which
pane is which, not as a product decision. Pane identity is carried by the pane's own title text
and its surface/border instead.

**Provenance (do not mis-cite).** The **light** column is measured from the artwork. The **dark**
column is **derived**, not measured — all eight review diagrams are light-only. Do not present the
dark values as "what the design says"; they are this ADR's extension of the system to a theme the
artwork never covered.

### 1.2 Layer tokens

The elevation axis is already in `globals.css` and must be used in this order — never invent a
new grey for a new surface:

```
--color-bg              (base)
  < --color-surface     (panel)
    < --color-surface-overlay  (raised control, hover fill, activity bar)
      < --color-border  (separator)
        < text          (primary / secondary / tertiary)
```

### 1.3 Density (decided 2026-10-30: looser, toward the diagrams)

Chrome spacing moves **up**: dominant gap **12px** (`gap-3`), control padding `px-3 py-2`, toolbar
rows `h-9` (was `h-7`), radius up one step (`sm 6 / DEFAULT 8 / md 10 / lg 12 / xl 14`), and
shadows softer and wider (a `0 2px 8px` family instead of `0 1px 3px`). Still a 4px grid — no
3px/5px/7px one-offs.

**Hard exception: the sidebar keeps its compact rhythm.** At the 192px minimum content width the
search row must keep a ≥80px query field (§8), and loosening its gaps is exactly what pushes it
under that floor — the same arithmetic that already forced `gap-1` over `gap-1.5` in
`SidebarSearch`. Loosening is therefore scoped to toolbars, dialogs, and the editor/preview
chrome; the sidebar column and its rows stay at 4/8px. Raising the sidebar's minimum width is the
only way to loosen the sidebar too, and that is a separate decision — do not smuggle it in here.

**The sidebar is exempt from DENSITY only — not from the radius step.** `borderRadius.DEFAULT` is
the global `rounded` class, so it reaches nearly every container, the sidebar included; the sidebar
follows `DEFAULT 6 → 8` like everything else. What the sidebar keeps is its 4/8px spacing rhythm
and its 28px rows. Radius is not part of the density budget.

**Icon and target sizes.** Icons move to **16px** (they are 11–14px today: `Search size={13}`,
`FileText size={14}`, `Replace size={11}`) and toolbar rows to `h-9` = 36px. This is the design
doc §2 mandate of 16–18px icons and 32–36px hit areas — today's `h-7` (28px) rows and 13px icons
are both below it, which is part of why the app read as cramped next to the diagrams. The sidebar
exception above therefore also keeps 28px rows: that satisfies WCAG 2.5.8 (24×24) but not the
design doc's own 32px preference. Constraint wins over preference; recorded so it is not later
filed as a bug.

**Implemented 2026-10-31 (PLAN C23) — the four numbers, pinned:**

- **Hit areas.** `ui/button.tsx`: `sm` 28 → **32px** (`h-8`), `md` 32 → **36px** (`h-9`), icon
  28 → **32px** (`h-8 w-8`); `ui/input.tsx` 32 → **36px** (`h-9`), so a dialog's input and its
  default button share one height. The icon button is **32px, not 36px**: a toolbar row is `h-9`
  _including_ its 1px bottom border, so its content box is 35px — a 36px target would overflow the
  row and overlap the separator. 32px is the lower end of the mandated 32–36px band and keeps
  E8 ("toolbar buttons ≥ 32px") true.
- **Icons.** 16px on the **chrome main controls** — the three bars' icon buttons and the sidebar
  header's four commands. Menu items and list rows keep their **13px** inline glyphs on purpose
  (PLAN C23): a menu row is 28px tall, and scaling its glyph would fatten the menu without
  enlarging the row.
- **Bar heights.** The **global bar stays 38px** (`--titlebar-height` — it is the window drag
  region); the **two pane bars are `h-9` = 36px**. Three bars, three documented heights, not an
  accident: the global bar is not a peer of the pane bars (it is mounted in every view mode and
  spans the whole content area), so "the pane bars are peers of equal height" (F10) applies to the
  pane bars alone.
- **Radius / shadow.** `borderRadius` `sm 4 → 6`, `DEFAULT 6 → 8`, `md 8 → 10`, `lg 10 → 12`,
  `xl 12 → 14`; the one elevation shadow family became `0 2px 8px` + `0 1px 2px`
  (`shadow-linear-lg`), so the tooltip, the status-bar popovers and the app banner no longer
  carry a second, harder Tailwind `shadow-lg`.

### 1.4 Iconography

An icon must disambiguate, not decorate. Two adjacent controls whose icons are the same glyph
read as the same action. Concretely: Quick Open (`⌘K`) and in-document Find (`⌘F`) sit one
button apart in the editor toolbar, so Quick Open is a document glyph (`FileText`), **not** a
second magnifier. `List` is reserved for the bullet-list formatting action in the same toolbar.

### 1.5 Single source of truth for design tokens (normative)

Design tokens live in **exactly one place**: the CSS custom properties in `globals.css`. Tailwind
must **reference** them, never restate them.

> **Tailwind v4.3.3 premise (corrected 2026-10-31, PLAN C27).** The repo runs Tailwind **v4.3.3**
> (`globals.css` opens with `@import 'tailwindcss'` + `@config`). v4 is CSS-first: the JS file is
> pulled in by `@config`, the `dark:` variant comes from
> `@custom-variant dark (&:where(.dark, .dark *))` — the v3 `darkMode: 'class'` config key is a
> **no-op** in v4 — and a colour utility compiles to `color: var(--token)`. Alpha modifiers compile
> to `color-mix(...)`, not to `rgb(... / a)`.

```
globals.css           --color-accent: #2563eb;
tailwind.config.cjs   accent: { DEFAULT: 'var(--color-accent)' }
```

Three rules follow. All three were violated before 2026-10-31 and are now satisfied (PLAN C22).

1. **Never hardcode a design colour in `tailwind.config.cjs`.** It used to carry a stale
   `text.tertiary: #9b9b9b` — the very 2.59:1 value §7.1 exists to remove — while `globals.css`
   carried the corrected one. Two copies of a token drift, and this pair already had. The config now
   holds exactly one colour entry, `accent.DEFAULT`, pointing at the CSS variable.
2. **Reference the CSS variable directly.** v4 emits `color: var(--color-accent)` for a bare `var()`,
   and compiles alpha modifiers (`bg-accent/20`, `border-accent/40`) to
   `color-mix(in oklab, var(--color-accent) 20%, transparent)` — the alpha survives. The v3
   `<alpha-value>` + `--color-*-rgb` channel-variable idiom is therefore **not required** here; it
   still compiles, but it demands a second, hand-maintained copy of every colour, so it is rejected.
3. **Hardcoded hex cannot respond to `.dark`.** A hex literal is the same value in both themes;
   only a variable reference changes with `.dark`. Referencing the variables fixes the theming of
   those ~35 call sites as a side effect.

**Verification:** `tailwind.config.cjs`'s `theme.extend.colors` contains **no hex literal**, and
`accent.DEFAULT === 'var(--color-accent)'` — both asserted by a unit test
(`src/renderer/src/styles/contrast.test.ts`). The utility class names (`text-accent`, `bg-accent`, …)
still exist and now resolve to the variables, so grepping for them proves nothing. See ADR-0025 F1/F2
and PLAN C22 / C27.

## 2. The activity bar (sidebar icon column)

The sidebar is two parts: a **48px activity bar that is always present**, and a **content panel**
that mounts only while the sidebar is open.

### 2.1 ARIA model: tabs, not toggle buttons

The activity bar is a vertical `tablist` of `role="tab"` buttons; the content panel is a
`role="tabpanel"`. `aria-pressed` is **wrong** here even though the icons also behave like
toggles:

- VS Code's activity bar is literally `role="tab"` + `aria-selected` + `aria-expanded`
  (its tablist container exists too — the claim that VS Code omits `tablist` is false).
- `aria-pressed` describes a button whose own state changed, not a control that selects one of
  several panels. Screen-reader users lose the "1 of 2" context.

| attribute       | value                                              | rule                                                                                                                          |
| --------------- | -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `aria-selected` | `open && view === id`                              | Collapsed ⇒ **false for both tabs**. Never report a selected tab with no panel.                                               |
| `aria-expanded` | same as `aria-selected`                            | Carries the "selected but hidden" collapse state that `aria-selected` alone cannot express.                                   |
| `aria-controls` | `sidebar-panel-<id>` on the selected tab only      | Exactly one panel is mounted; putting it on the unselected tab emits a dangling IDREF.                                        |
| `tabIndex`      | roving: `0` on the selected tab, `-1` on the other | When nothing is selected (collapsed) the **first** tab keeps `tabIndex=0`, or the whole bar becomes unreachable (WCAG 2.1.1). |

`aria-controls` + `role="tabpanel"` is an ARIA APG completion, **not** VS Code parity — VS Code
has zero hits for either in `parts/`. We add them anyway; the cost is nil and the association is
what makes the tab model true rather than decorative.

`role="tabpanel"` on the `<aside>` overrides its `complementary` landmark. **Accepted.** The
sidebar is a switcher first and a landmark second; tests query `role="tabpanel"`.

### 2.2 Container element

The tablist is a plain `<div role="tablist" aria-orientation="vertical">`:

- Not `<aside>`: a collapsed sidebar must not leave an `<aside>` in the tree.
- Not `<nav>`: `role` silently overrides the navigation landmark, so it would be decorative
  markup pretending to help. Two items do not justify a landmark.

### 2.3 Keyboard

↑/↓ move between tabs and **auto-activate**, keeping focus on the tab (APG automatic activation;
VS Code's `ActionBar` does the same in `actionbar.ts`). Enter/Tab then moves into the panel.
Omitting arrow keys would be a double deliberate deviation from both the APG and VS Code.

### 2.4 Click behaviour

Clicking the already-active icon **collapses** the panel — VS Code's default
`workbench.activityBar.iconClickBehavior: 'toggle'` (`paneCompositeBar.ts`).

### 2.5 Focus ownership (normative)

Switching views is not one thing; it is four call sites with three different correct answers.
Any blanket "move focus on every view change" effect is wrong.

| path                           | focus lands on     | mechanism                                                     |
| ------------------------------ | ------------------ | ------------------------------------------------------------- |
| activity-bar click / ↑↓        | **the tab itself** | nothing moves it (APG automatic activation, so ↑↓ can repeat) |
| `⌘⇧F` → Search                 | the query input    | `requestSearchFocus()`                                        |
| `⌘⇧E` → Files                  | the panel          | `requestPanelFocus()`                                         |
| tree ▸ "Search in This Folder" | the include row    | `requestScopeFocus()`                                         |

The last row is why the blanket effect cannot exist: that action writes a scope and parks the
caret in it, and a generic view-change focus move would steal it. `requestPanelFocus()` bumps an
explicit `panelFocusNonce` that only `Sidebar` consumes. **No opt-out flags, no
`skipFocusMoveRef`** — a caller that wants the panel says so.

### 2.6 Recovery entries live on the activity bar

Reset-width and collapse are reachable from the activity bar's context menu, because the content
panel — and therefore its resize-handle menu — does not exist while collapsed. The resize-handle
menu keeps its own copies for the expanded state.

> **testid rule:** the two entries must **not** share testids across the two menus. Both menus are
> mounted while expanded, so duplicate `data-testid` values make Playwright's `getByTestId` throw
> a strict-mode violation. Activity-bar copies are `activity-reset-sidebar-width` /
> `activity-collapse-sidebar`; the panel's stay `side-reset-sidebar-width` / `side-collapse-sidebar`.

### 2.7 macOS traffic lights

macOS runs a custom title bar with `trafficLightPosition {x:16,y:16}`, so the top-left of the
first pane is covered. The activity bar clears it with
`padding-top: calc(var(--titlebar-height) + 0.5rem)` on macOS only.

> **`calc()` gotcha (bit us once):** CSS requires whitespace around `+` and `-`.
> `pt-[calc(var(--titlebar-height)+0.5rem)]` is an **invalid declaration** and the browser drops
> the whole thing silently. In Tailwind arbitrary values a space is written `_`
> (`pt-[calc(var(--titlebar-height)_+_0.5rem)]`). Prefer an inline `style` when in doubt.

The activity bar must **not** carry `.titlebar-drag` — tests locate the drag region by class and
would hit the 48px column first.

### 2.8 Widths

Default total 288px (48 bar + 240 content), minimum 240 (48 + 192). The 48px column is new, so
both numbers moved up by 48 from the old single-pane 240/180 — the content panel keeps its old
240/192.

## 3. Global shortcuts: one owner per key

A key with two independent handlers double-fires, and a key with no handler is a lie if the UI
advertises it.

1. **Exactly one owner.** `⌘B` (toggle panel) exists **only** in the renderer; there is no
   `CmdOrCtrl+B` menu accelerator. `⌘\` stays the menu-routed twin of the same action. Both
   collapse/expand the **content panel** — the activity bar is permanent. (Design docs wording
   "toggle the whole sidebar" is wrong; VS Code's `ToggleSidebarVisibilityAction` toggles
   `Parts.SIDEBAR_PART` and keeps the activity bar, which is exactly why that entry lives in the
   activity-bar menu.)
2. **No advertised-but-unimplemented bindings.** The editor context menu used to print `⌘B`,
   `⌘I`, `⌘E`, `⌘K` next to Bold / Italic / Inline code / Link. None were wired, and two are
   taken by other commands (`⌘I` = file details, `⌘K` = Quick Open). Those four labels were
   removed. A tooltip naming a binding that does something else is worse than no tooltip.
3. **Breaking changes are announced, not smuggled.** `⌘⇧E` moved to Files view (VS Code
   `workbench.view.explorer`), so **Export as HTML moved to `⌘⇧X`**. The menu item id and IPC
   channel are unchanged; the accelerator and the on-screen hint moved. Documented in the
   release notes.

## 4. Control reuse (C19)

**Before adding any input, toggle, button, or menu, look in `src/renderer/src/components/ui/`.**
Available primitives: `Button`, `SearchInput`, `IconToggleGroup`, `InputContextMenu`, `Tooltip`,
`ContextMenu`, `Dialog`, `MatchCounter`.

If no primitive fits, add it to `components/ui/` first — do not hand-roll an equivalent inside a
feature component. Historical counter-example, now fixed: `SidebarSearch` had its own
`<input>` + magnifier + clear button while `SearchInput` already existed and the editor and
preview find widgets already used it. The three find surfaces are now literally the same
component; that is what keeps them from drifting.

Review checklist item for UI PRs: _did this reuse `components/ui`, and if not, why?_

## 5. Typography (C17)

### 5.1 Type scale and the 11px floor

`xs(12) / sm(14) / base(16)` from Tailwind defaults, plus `2xs` = **11px** — a global token, not
a sidebar value. **Nothing anywhere in the UI renders below 11px.** Metadata, badges, counters,
and captions all obey it.

Raising `2xs` from 10px to 11px touched every `text-2xs` in the app at once. Where that cost
horizontal room (compact rows, scope labels), the fix is local — wider container, truncation, or
a shorter string — **never** reverting the global token.

### 5.2 Weights and leading

UI labels `medium(500)`, body `normal(400)`, headings may use `semibold(600)`. Leading 14–20px
inside controls, 1.5 for long prose.

### 5.3 Fonts: system stacks only (C15)

```
--font-sans: -apple-system, BlinkMacSystemFont, 'Segoe UI', system-ui, sans-serif
--font-mono: ui-monospace, SFMono-Regular, Menlo, Consolas, monospace
```

`Inter`, `JetBrains Mono`, `Fira Code`, and `Cascadia Code` were listed but **never shipped** —
no `@font-face`, no font package, no `.woff` in the repo. They only ever applied on machines that
happened to have them installed, which made the rendered UI machine-dependent while looking
configured. System stacks are the honest contract: zero bytes, zero licence question, correct
per-platform fallback.

Any font that is added later must be bundled in-repo. A bare `font-family` name is not a font.

**CJK stays on the system stack (decided 2026-10-30).** The review diagrams declare
`Noto Sans CJK SC, Microsoft YaHei, sans-serif`. That stack is **not adopted**: the repo ships no
`.woff`, so those names are fallbacks that resolve only on machines that happen to have them —
precisely the machine-dependent rendering this section exists to prevent. CJK therefore continues
to fall through `system-ui` / `Segoe UI` to PingFang (macOS) and YaHei (Windows): zero bytes,
correct per-platform face. If a specific CJK face is ever wanted it must be **bundled** (a
subset), never merely named.

## 6. Motion (C18)

- **Keep** motion that responds to a user action: hover colour transitions, dialog entry, the
  content panel's `animate-slide-in-left` when it expands.
- **Forbid** decorative autoplay: looping animation, self-initiated movement, anything that runs
  with no triggering input.
- **Degrade** through exactly one mechanism — the `prefers-reduced-motion: reduce` catch-all in
  `globals.css`. No per-component opt-outs, no second media query.

Durations are `0.01ms`, not `0s`: a zero duration never fires `animationend`/`transitionend`,
which would leave any cleanup that waits on those events hanging forever.

## 7. Accessibility floor (C12–C14)

1. **Contrast.** Body text ≥ 4.5:1 (WCAG 1.4.3), measured against **every** surface in §1.2 —
   `bg`, `surface`, `surface-overlay` **and** `accent-muted` — not against `bg` alone. Under the
   §1.1 palette the light theme lands on `#536176` for **both** secondary and tertiary
   (**5.86 / 6.29 / 5.59 / 5.58** on those four surfaces), and the dark theme on `#a0adbd`
   (**8.12:1** on `#0f1419`) / `#8893a2` (**5.94:1**). The diagrams' `#94a3b8` (2.39:1), `#8893a2`
   (2.90:1 on light), `#68778d` (4.25:1) and `#a2acbb` (2.14:1) are **rejected on the light
   theme** — copying the artwork would have re-introduced the very violation this item removed
   (the original failing value was `#9b9b9b` at 2.59:1). A third grey step that is both
   distinguishable and compliant does not exist on light; the hierarchy is a deliberate casualty
   of the floor. Semantic colours are held to **3:1** (WCAG 1.4.11) as indicators and to 4.5:1 as
   a fill under white text — never to 4.5:1 as text (§1.1). **All ratios quoted in this ADR are
   generated by the unit test in PLAN C25; re-measure after any palette change rather than
   editing the numbers by hand** (hand-copied ratios in this repo had already drifted by
   0.03–0.04).
2. **One focus indicator.** Inputs carry `.focus-ring`. A container must not _also_ paint
   `focus-within:border-accent` — two indicators on one box is noise (WCAG 2.4.7). Note that
   `:focus-visible` on a text input matches mouse clicks too in Chromium, so this overlap is the
   common case, not a rare one.
   **`focus:ring-0` is forbidden** — it removes the indicator entirely, which is worse than two.
   `EditorPane.tsx:1013` ships it today on the document-title input: a straight 2.4.7 failure.
   C11 converted only 6 call sites; ~15 `outline-none` sites still hand-roll their own ring
   (ADR-0025 F4, PLAN C24).
3. **Reduced motion.** See §6.
4. **The floor must be machine-checked, and the theme must be declared.** Two gaps found on the
   second pass (ADR-0025 §4.1 F14/F15): **nothing asserts contrast anywhere in `src/`**, and
   `color-scheme` is never declared, so native scrollbars, form controls and spellcheck UI do not
   follow `.dark`. Add a unit test over the token pairs (PLAN C25) and declare `color-scheme`
   (PLAN C26). Windows `forced-colors` mode is likewise unhandled (F16) — at minimum, focus rings
   must survive it.

## 8. Search view layout (C9/C10)

The primary row holds magnifier + query + `Aa` + replace chevron. Whole word (`ab`) and regex
(`.*`) live on a **second, always-visible row** rather than being buried behind the details
disclosure — discoverability was the point of splitting them out.

At the 192px minimum content width the primary row must not overflow and the query input keeps
≥80px. If details do not fit, collapse the details block; **never** shrink the type to make room
(that would fight §5.1).

## 9. Empty state (C8)

With no document open the **global bar** shows only what can act: sidebar toggle, Quick Open (with
its `⌘K` chip) and Close. **Save / Save-As / Reload / file details / export / the view switch /
find / replace / read-only toggle are all gated** — the first group on `activeDocumentId`, the view
switch on the document branch itself — together with the dividers that precede them: a lone
divider floating after a chip is worse than none.

**Find is gated too, and that is correct**: with no document there is no content to search, so a
find entry point would be a dead control — the same reasoning that removes the read-only toggle
(there is no document to protect). The design doc's empty-state list used to keep Find and to
attribute the navigation entries to the _editor_ pane bar; both were corrected on 2026-10-31
(review round 21) against `EditorPane.tsx:665` and the §9 gates.

New/Open are deliberately **not** added to the empty-state toolbar: the sidebar header carries
them and `⌘N`/`⌘O` reach them from anywhere. Adding duplicates would dilute the four-cluster
grouping that makes the toolbar scannable.

## 10. Pane toolbars: each pane owns its own bar

The 2026-10-27 design text modelled the chrome as **one shared tool band** across the top of the
content area, with the preview having no persistent bar at all (R3: find only as a floating
widget). Review on 2026-10-30 reversed both halves. The layout is now two peer pane bars under a
slim global bar:

```
┌────────────────────────────────────────────────┐  global bar (always mounted)
│ ☰  QuickOpen ⌘K   save  details ⌘I   close   [source│split│preview] │
│                                      export ⌘⇧X  ← edit-only only   │
├───────────────────────┬────────────────────────┤
│ editor pane bar       │ preview pane bar       │  peer bars, each owns its pane
│ format  find/replace  │ find  export  copy  ⋯  │
│ undo/redo             │                        │
│ read-only             │                        │
```

> The `export` button is drawn on both bars because it is **one action** — but only **one** of
> them shows it at a time: the global bar's copy appears only in **edit-only** mode (the preview
> pane is `hidden` then, so there is nothing to inspect); as soon as the preview is visible the
> button lives on the **preview bar**, next to the rendering it exports. See §11 trade-off 46.
>
> **Implementation (amended 2026-10-31, review round 21): the global bar is not a new component.**
> The global `TitleBar` was deleted with D22 and `ui/titlebar-deleted.test.ts` pins that deletion —
> reviving it would reintroduce the fourth horizontal bar the plan removed. The row that already
> exists — `EditorPane.tsx:986-1160`, mounted **outside** the split container (`:1276-1299`) and
> therefore in all three view modes — **is** today's de-facto global bar. C20 re-scopes that row
> (cross-pane commands stay on it, editor-only clusters sink into the editor pane bar) instead of
> adding a bar. Do not introduce a `TitleBar` component; the guard test forbids it.
>
> **Bar heights (added 2026-10-31, PLAN C23 boundary ③).** The global bar is **38px**
> (`--titlebar-height` — it carries the window drag region and the macOS traffic-light clearance);
> the two pane bars are **`h-9` = 36px**. So the three bars are deliberately **not** all equal:
> "the pane bars are peers of equal height" (F10) binds the **two pane bars to each other**, and
> the global bar is not a peer of them — it is mounted in all three view modes and spans the whole
> content area. Pinning all three to one number would either clip the drag region or waste 2px on
> every pane bar.

- **Global bar** (single- or split-pane, always mounted): sidebar toggle, Quick Open with its
  permanent `⌘K` chip, save / save-as / reload, **file details (`⌘I`)**, close, and the
  source/split/preview switch. Document title and truncated path live here. In single-pane mode it
  stays — dropping it would strand save and export. **Export HTML lives here only in edit-only mode**
  (the preview pane is `hidden` then, so there is no rendered result to inspect); when the preview is
  visible the export button lives on the preview bar instead — see §11 trade-off 46.
  **File details moved here from the editor pane bar on 2026-10-31 (review round 20, user decision):
  the editor pane bar is absent in preview-only, so a document-metadata entry parked there would be
  unreachable in one of the three modes — see §11 trade-off 51.** Its UI wording is the existing
  `editor.fileDetails` — “File details” / 「文件详情」, not “document details”.
- **Editor pane bar**, attached to the editor pane: Markdown formatting, the find/replace group,
  undo/redo, read-only toggle. Gated per §9 when no document is open.
  **Amended 2026-10-31 (review round 16):** the find **options** (`Aa` / whole word / regexp) move
  **out of this bar and into the find panel** — VS Code's find widget, Chrome/Edge and Firefox's
  find bar, Obsidian's Inline Search and Sublime's find bar all keep the options next to the find
  input, never on a toolbar. The options are only meaningful while the find panel is open, so a
  permanent bar row would leave dead controls on screen; and this bar's width is already committed
  to 16px icons and 32–36px hit targets (§8, §10 trade-off 24). The bar keeps the **find** and
  **replace** entry points; the panel keeps the options.
- **Preview pane bar**, attached to the preview pane: find, export HTML, copy rendered content,
  and `⋯` more for low-frequency commands. **Amended 2026-10-31 (decision 方案乙):** the find
  button **expands the preview find panel anchored under the pane bar** — the panel is no longer a
  floating `PreviewFindBar` widget anchored to the top-right corner. The find implementation is
  reused as-is; preview find stays **read-only, never replace**. Keep the `find-surface` class on
  the panel (an e2e contract asserts it) and add a preview-specific positioning override — do
  **not** change `.find-surface` itself, it is shared with the editor's CodeMirror find panel.
  **Amended 2026-10-31 (review round 23, C33):** the preview **is** the export's rendering — the two
  share the `github-markdown-css` sheet, the same sanitized HTML, the same mermaid bake **and the same
  `.markdown-body` override sheet** (`styles/markdownExport.css`, inlined verbatim into the export).
  This is now an **executable assertion**, not a promise: `e2e/specs/export-parity.e2e.spec.ts` renders
  the same document twice — in the live preview and in the real exported HTML opened in a second
  window — and compares the **computed** styles of the code block and of a highlight.js token. Any
  future divergence (a sheet added to one side only, a token renamed, a theme rule that only exists
  in the app) fails that spec.
- **Bar width budget (added 2026-10-31, review round 22).** Every bar needs an explicit **item
  budget**, because the three bars do not share the same width. The **global bar spans the whole
  content area** in every mode (it is today's always-mounted header row, re-scoped — trade-off 52),
  while in split mode the **editor pane bar owns only the editor column**, whose width is
  `splitRatio` — a local state the user can drag between **0.2 and 0.8** (`EditorPane.tsx:574` /
  `:584`). The editor pane bar must carry the formatting cluster (**7** buttons — h1 / bold /
  italic / code / link / list / task, `EditorPane.tsx:1070-1116`) plus find / replace / undo / redo /
  read-only ≈ **12 items**; at the 32–36px hit areas this design prefers (§2) that is **≈420px**,
  which does not fit a 20% column. The cluster is currently collapsed by a **viewport** breakpoint
  (`hidden md:flex`, `:1071`) — a window-width test that cannot see the pane width, so it still
  renders in a narrow split column. Prescription: the editor pane bar collapses **by pane width**,
  not by viewport — the formatting cluster folds into a single `Format` dropdown (7 → 1), and the
  bar keeps a VS Code-style overflow (`…` past a 9-item cap, `editorTabsControl.ts:305-335`). The
  **global bar needs no overflow**: its command set is a strict **subset** of today's header row,
  which already renders the same commands plus find / replace / read-only / the formatting cluster
  with no overflow and no `…`.
  **Amended 2026-10-31 (C20 implementation) — the pane bar's collapse is width-driven in TWO stages, not a count-based overflow.**
  The prescription above names two mechanisms: the formatting cluster folds into a `Format` dropdown, and the bar "keeps a
  VS Code-style overflow (`…` past a 9-item cap, `editorTabsControl.ts:305-335`)". Implemented as a literal 9-item **count**
  cap, that overflow would be **unreachable**: the first stage already reduces the bar to 6 items (Format + find / replace /
  undo / redo / read-only), so nothing could ever cross 9 — dead code by construction. The governing rule of trade-off 54 is
  _"collapse by pane width, not by viewport"_, and the 9-item figure is VS Code's **rationale for folding at all**, not a
  trigger; so the overflow is triggered by width, exactly like the fold:
  - **wide** (≥ 420px): the full 12-item budget.
  - **folded** (< 420px): the formatting cluster folds into `Format` (7 → 1), leaving 6 items.
  - **minimal** (< 240px): undo / redo / read-only move into a `…` overflow (3 → 1), leaving 4 — the stage that actually keeps
    a 20 %-column (`splitRatio` down to 0.2) from clipping the bar.
    Find / replace stay inline in every stage: they are the primary entry points and must never be more than one level deep.
    Two implementation facts worth recording: the formatting buttons are **disabled**, not hidden, while the pane is read-only
    (a hidden cluster made the bar jump when the mode changed), and the read-only toggle's test id moved from
    `toggle-editable-btn` to `editor-readonly-btn` now that it lives on the pane bar.
    **Amended 2026-10-31 (review round 17) — "export HTML" is ONE action whose entry point follows the preview's visibility, so only one export button is ever on screen.**
    The preview and the exporter share **the same `github-markdown-css` sheet** (`globals.css` §"markdown styling now comes from
    github-markdown-css … the same sheet the exporter uses"; `MarkdownPreview.tsx` repeats it), **the same sanitized HTML source**
    (`exportStore`'s canonical preview HTML) and **the same mermaid bake** (`exportBake.prepareExportHtml`) — so the preview
    shows the export's **content, structure, theme and overall layout**. **Amended 2026-10-31 (review round 18):** the preview
    is _not_ pixel-identical to the exported file — the exporter inlines **fewer** stylesheets than the app applies
    (it misses `highlight.js` token colours, the `.markdown-body` overrides in `globals.css`, and it leaves KaTeX's
    `url(fonts/…)` unresolved; `data-theme` also sits on `<html>` while `.markdown-body` sits on `<body>`). Closing that gap is
    **C33 (export parity)**, and until it lands an **export-time preview** — not the app preview — is the only honest way to show
    the exported result. Placing the action next to the live rendering is still the mainstream pattern (Figma's export panel
    sits against the artboard; Photoshop's export dialog carries a live preview): a button's position is decided by the
    action's **precondition** (what the user must see first), not only by its target. Therefore: **preview visible
    (preview-only / split) ⇒ the entry is on the preview bar;
    edit-only (the preview pane is `hidden`) ⇒ the entry stays on the global bar**, where export is a plain file operation with
    no visible effect to inspect and the `⌘⇧X` shortcut must not be stranded. The **visible** button always carries the `⌘⇧X`
    label. If both bars ever showed it, it would be one action with one implementation (`setExportOpen(true)`) and one wording
    (`editor.export`) — never a second export path — and two peer toolbars must not carry the same button side by side
    (VS Code's Save appears once). The export also needs an **export-time preview** (a `srcdoc` iframe inside the export dialog,
    always rendered with images inlined), because the app preview is not byte-identical to the exported file in three respects:
    the theme can be overridden in the dialog, the preview renders mermaid lazily while the export bakes all of it, and
    non-inlined images are rewritten to relative paths.

**Why the reversal.** The preview bar was deleted on the strength of a claim that it was
"invisible with no buttons in it". That is false against 图 02, which draws a populated preview
band (find / export / copy / more). A decision taken on a misreading of its own artefact is not a
decision, so it is undone rather than defended. Persistent reachability of preview actions
outweighs the ~32–36px of vertical space the bar costs.

**Accepted cost.** This diverges from VS Code, whose preview has no persistent bar. Each pane grows
by roughly one control row. Copy appears in both the preview bar and the preview context menu —
duplication accepted for reachability. Export HTML appears **once at a time**: on the preview bar
while the preview is visible, on the global bar in edit-only mode (see §11 trade-off 46). The export
is one **action** with one dialog, one implementation and one wording — never two features.

**The export dialog carries the export-time preview (implemented 2026-10-31, PLAN C20 ⑨).** It
renders the **export's own** stylesheet inside a **shadow root** (§11 trade-off 49), so what is on
screen is what the file will contain — the app's own styling cannot leak in, which is the whole
point of the feature. Three deviations are stated in the UI rather than papered over:

- **W1 theme** — the dialog's theme selector can force light/dark, so the preview follows the
  _selected_ theme, not the app's.
- **W2 diagrams** — the app preview renders diagrams lazily (on scroll) while the export bakes the
  whole document, so the preview **bakes first** and shows every diagram; the note says so.
- **W3 images** — the preview always renders the **single-file form** (images inlined). In the
  non-inline mode the export rewrites `appdoc://` to a _relative_ path, which inside a shadow root
  would resolve against the host document's base URL and break every image.

One source of truth: `buildExportParts()` returns `{ theme, lang, body, css, fontCss, rootVars,
containerCss, printCss }` and **both** consumers assemble from it — `buildStandaloneHtml()` (the
file) and the shadow-root preview (the dialog). The `@font-face` half of the KaTeX sheet is
returned separately (`fontCss`) because a shadow root does not register fonts; the document-level
custom properties land on `:host` and the container declarations on the preview container, because
`body` does not match inside a shadow root.

Three implementation rules follow from that structure, each one measured rather than assumed:

- **The host font sheet is owned by the preview, not by the document.** It is ~254KB of base64
  font data; leaving it in `document.head` after the dialog closes would pin it for the whole
  session. It is removed on unmount — deferred by one tick, because React's StrictMode
  double-invokes effects (mount → cleanup → mount) while `parts` stays identical, so an immediate
  removal would leave the second mount with no `@font-face` at all.
- **A theme switch must not rebuild the body.** The shadow root's skeleton (four `<style>` parts +
  the container + `.markdown-body`) is created once and the pieces are updated in place. Only
  `data-theme` and the stylesheets change on a theme switch; rewriting `innerHTML` would re-decode
  every inlined image and reset the user's scroll position. Guarded by a unit test that compares
  DOM node identity across a theme change.
- **The body and the theme are orthogonal.** `buildExportBody()` is exported on its own and
  `buildExportParts({ body })` accepts a pre-built one, so toggling the theme in the dialog reuses
  the body instead of re-running the image-inlining IPC.
